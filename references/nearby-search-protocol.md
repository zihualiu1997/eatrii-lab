# 附近门店高召回搜索协议

本协议只在用户提供位置且需要具体门店时读取。目标是在现有 `web-search` / `read-page` 范围内最大化召回、留下可审计记录，再由 Eatrii 排序；网页搜索无法证明现实门店全量，因此只能写“本轮检索到”。

## 一、建立三个空间锚点

1. **精确锚点**：具体建筑、园区入口或送达地址。
2. **别名锚点**：建筑别名、所在园区、街道或社区。
3. **邻近锚点**：邻近商场、餐饮聚集区、社区或地铁口。

- 先用位置原文搜索同城结果，确认城市、区和建筑；同名地点无法消歧时停止并询问。
- 邻近锚点只能来自搜索结果或用户上下文，不得凭空猜测。
- 商务宴请可把第三锚点扩大到相邻商圈；普通到店和外卖优先紧邻范围。

## 二、七组等额查询词典

每个空间锚点都执行以下七组查询，每组一个逻辑查询，不向热门或连锁类别追加预算。

| 组别 | 必含词或同义方向 |
|------|------------------|
| 全餐饮 | 美食、餐厅、餐饮、吃饭、快餐、食堂 |
| 米饭快餐 | 猪脚饭、隆江猪脚饭、烧腊、盖饭、拌饭、木桶饭、煲仔饭、便当、自选快餐 |
| 粉面饺子 | 云南米线、过桥米线、米粉、汤粉、面馆、水饺、馄饨、螺蛳粉 |
| 家常小炒 | 小炒、快餐小炒、湘菜、川菜、粤菜、客家菜、农家菜、家常菜 |
| 麻辣拌食 | 拌将、拌将麻辣拌、拌将麻辣烫、拌将外卖、拌将水煮菜、干拌、麻辣烫、冒菜、麻辣香锅、卤味 |
| 汤粥清淡 | 粥、汤饭、蒸菜、汤粉、轻食、沙拉、炖汤 |
| 其他正餐 | 火锅、烧烤、日料、东南亚菜、西餐、茶餐厅、融合菜 |

查询模板：

```text
“<空间锚点> <该组查询词> 门店 地址”
```

- 可以在一个逻辑查询里并列同组词，但不得混入“推荐、榜单、网红、必吃、评分最高”等词。
- 搜索结果来自任何网页时一律平行收集；平台名称和出现顺序不构成质量权重。
- 摘要出现具体店名、分店或地址线索即可进入候选台账，后续再核验。
- 外卖型品牌可能没有沿街店招。外卖分支发现品牌线索时，用该分支的补查额度执行“`<空间锚点> <品牌> 外卖 地址 送达范围`”；查到后照常入池，不得因没有到店页面而丢弃。

## 三、查询矩阵与停止条件

- 基础矩阵固定为 `3个空间锚点 × 7组餐型 = 21个逻辑查询`。
- 基础矩阵全部完成前，不得主推或按评分删店。
- 完成基础矩阵后，最多执行3次补查：优先空白餐型、地址不清的候选、用户已知漏店或疑似错分店。
- 用户给出已知漏店时，至少用一次“`<空间锚点> <完整品牌名> 地址`”和一次“`<空间锚点> <完整品牌名> 到店/外卖`”补查；两次都计入3次补查上限。额度不足或仍无可核验证据时，不得宣称该店不存在，覆盖状态保持“未搜完”。
- 三次补查都没有新增有效门店时，封闭候选池。
- 达到24次且最后一次仍有新增门店时，标记 `coverage_status: incomplete`；先交付临时结果，再询问是否继续深搜。
- 某组没有结果时保留空白记录，不把其他组的店复制过去充数。

## 四、候选台账

每家门店至少记录：

```text
名称｜分店｜地址文本｜城市/区｜餐型组｜服务方式（到店/外卖/未知）｜空间锚点｜发现查询｜来源URL
推广/榜单标记｜营业｜价格｜步行/送达｜排队｜座位/包间｜核验状态
```

- 推广、榜单、评分、评论量和网红标签仅作为来源属性，永远不参与排序加分。
- 来源数量只影响信息置信度，不代表门店更好。
- 无法确定分店或地址的候选可以保留，但核验状态必须是“待核验”。
- 只有存在可核验门面或到店信息的候选才能进入“出去吃”排序；只提供配送的候选保留在台账中，但仅进入“外卖”排序。服务方式无法核验时写“未知”。

## 五、去重与位置过滤

1. 统一全半角、大小写、空格和常见括号，但保留品牌与分店名。
2. 优先以“标准化名称＋分店/地址”去重。
3. 同品牌不同分店必须保留；地址不明的同名店不得贸然合并。
4. 明确位于其他城市、区或远离三个锚点的结果才可删除，并记录删除原因。
5. 餐型相同不是重复门店；不得用一家猪脚饭代表附近所有猪脚饭。

## 六、封池后核验与排序

- 候选池封闭后才调用 `read-page`，先核验排序前10家；失效候选由后续候选递补。
- 核验具体分店的营业、价格、菜单、排队、座位、环境和来源时间，不用品牌总体信息替代分店。
- 没有当前证据的字段写“未知”，不能由旧评论推算实时分钟数。
- 先执行硬约束过滤，再按 Eatrii 主流程的场景顺序排序。
- 删除推广、榜单、评分、评论量和网红字段后重新排序，结果必须不变。

## 七、覆盖报告

正常输出只报告：

```text
本轮检索到 N 家｜基础矩阵 21/21｜补查 X/3｜覆盖状态：已封池/未搜完
```

- 常规回复显示最相关的10家；用户要求时再展开完整候选池。
- 不得使用“附近全部”“一共只有”“零遗漏”或“已穷尽现实门店”等表述。
- 已知门店未进入候选池即判定本轮高召回测试失败，补充锚点或查询词后重跑。

## 八、后续升级门槛

若人工真值仍有漏店，或多次达到24次仍未封池，记录为需要扩充 `tools.txt` 的证据。后续方向是服务端地图 POI 枚举、分页、自适应网格与路线核验；当前版本不得自行调用未列入 `tools.txt` 的地图接口。

建议下一阶段新增但当前不可调用：

- `map-enumerate-nearby`：使用高德 Web 服务在服务端解析位置，以餐饮类型、分页和自适应网格枚举 POI；Key 只存服务端 Secret。
- `map-route-matrix`：只对排序前候选核验步行或驾车路线。

高德 POI 2.0 官方说明同请求参数最多获取200条且不支持返回全量数据，因此即使升级也必须拆分网格并保留人工真值验收：https://developer.amap.com/api/webservice/guide/api-advanced/newpoisearch
