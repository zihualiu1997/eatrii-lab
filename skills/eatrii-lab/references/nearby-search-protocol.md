# 附近门店高召回搜索协议

本协议只在用户提供位置且需要具体门店时读取。目标是先用 `map-enumerate-nearby` 枚举高德餐饮 POI，再用 `web-search` 平行补漏，形成不受平台推荐顺序支配的可审计候选池。任何数据源都不能证明现实门店全量，正式表达只能写“本轮检索到”。正餐使用本协议第四、五节的21格矩阵；饮料场景保留本协议的位置、高德、锚点、台账和覆盖规则，但用[饮料检索与决策协议](beverage-protocol.md)的15格或9格矩阵替代第四、五节。

## 一、先唯一解析位置

1. 把用户给出的具体建筑、园区、街道或送达地址原样传给 `map-enumerate-nearby`。
2. 上下文中有城市时必须同时传 `city_hint`；不得省略已有城市信息。
3. 工具返回 `location_unresolved` 时停止具体门店检索，请用户补充城市、区、建筑或门牌，不从多个坐标中擅自选一个。
4. 只有用户明确拒绝位置时才跳过地图与网页门店搜索，退化为餐型方向。

高德枚举使用以下场景默认范围；用户主动给出范围时可覆盖，但不要把直线半径写成步行距离或外卖配送范围。

| 场景 | `scene` | 默认发现半径 |
|------|---------|-------------:|
| 普通出去吃 | `dine_in` | 1500米 |
| 外卖 | `delivery` | 3000米 |
| 普通客户或日常接待 | `business_casual` | 3000米 |
| 重要客户或正式宴请 | `business_formal` | 5000米 |

## 二、高德 POI 平铺召回

调用 `map-enumerate-nearby` 后，先把返回的全部 `pois` 写入候选台账，候选池封闭前不推荐、不打分、不按高德返回顺序截断。

- 单次工具响应默认最多交付250家。首次调用使用 `{address, city_hint, scene}`；`delivery.delivery_complete: false` 时必须继续调用同一工具并只传 `{next_cursor: previous.delivery.next_cursor}`，依次合并各页；直到 `delivery_complete: true` 才算候选交付完整。旧 `cursor` 输入暂时兼容但已弃用；地址与游标不得同时出现。续页只读进程内候选池，不得再次地理编码或调用高德。
- 游标只在插件内存中短暂保留，默认10分钟。游标丢失或过期时重新执行完整枚举，不凭第一页宣布封池。
- 工具固定枚举高德餐饮大类 `050000`，每页25条、同参数最多8页。
- 周边查询少于200条时直接闭合；第8页仍满25条时，工具改用矩形 POI 搜索并沿实际米数更长的方向自适应二分。
- 每个矩形仍到200条时继续拆分；小于约50米仍饱和、请求预算耗尽或服务失败时必须返回 `partial`。
- 所有结果优先按高德 POI ID去重；缺少 ID 时才回退到“标准化店名＋地址＋坐标”关联。随后重新计算到用户坐标的直线距离，并剔除发现半径之外的矩形角落结果。
- 高德页码、返回次序、评分、评论量、推广和综合权重不得进入 Eatrii 排序；最终候选按本技能自己的事实字段判断。
- `amap_enumeration_complete` 只表示本轮高德返回空间已闭合，不表示现实门店全量。

按返回状态继续：

| 状态 | 后续动作 |
|------|----------|
| `amap_enumeration_complete` 且 `delivery_complete: true` | 保留全部 POI，继续第三节网页补漏 |
| `amap_enumeration_complete` 但 `delivery_complete: false` | 沿 `next_cursor` 继续取页，暂不封池 |
| `partial` | 保留已返回 POI，记录 `partial_reasons`，继续网页补漏；总覆盖状态保持“未搜完” |
| `location_unresolved` | 等待用户补充位置，不开始网页门店搜索 |
| `provider_unavailable` 或工具不可用 | 不改用未授权地图接口；执行完整网页兜底，总覆盖状态保持“未搜完” |

`AMAP_WEB_SERVICE_KEY` 只能由插件进程的环境变量提供。不得要求用户把 Key 发在对话里，不得把 Key、含 Key 的 URL、请求日志或报错堆栈写入候选台账和回复。

## 三、建立三个网页空间锚点

高德 POI 解决平铺发现，网页搜索继续补充新店、外卖专营店、地图暂未收录门店与分店事实。三个锚点均从用户上下文、高德解析结果或当前网页证据获得，不得凭空猜测。

1. **精确锚点**：具体建筑、园区入口或送达地址。
2. **别名锚点**：建筑别名、所在园区、街道或社区。
3. **邻近锚点**：邻近商场、餐饮聚集区、社区或地铁口。

- 商务宴请可把第三锚点扩大到相邻商圈；普通到店和外卖优先紧邻范围。
- 网页结果必须核对城市和区；高德解析出的行政区可以帮助排除错城结果。

## 四、正餐七组等额网页补漏词典

每个空间锚点都执行以下七组查询，每组一个逻辑查询，不向热门、连锁或某个平台追加预算。

| 组别 | 必含词或同义方向 |
|------|------------------|
| 全餐饮 | 美食、餐厅、餐饮、吃饭、快餐、食堂 |
| 米饭快餐 | 猪脚饭、隆江猪脚饭、烧腊、盖饭、拌饭、木桶饭、煲仔饭、便当、自选快餐 |
| 粉面饺子 | 云南米线、过桥米线、米粉、汤粉、面馆、水饺、馄饨、螺蛳粉 |
| 家常小炒 | 小炒、快餐小炒、湘菜、川菜、粤菜、客家菜、农家菜、家常菜 |
| 麻辣拌食 | 拌将、拌将麻辣拌、拌将麻辣烫、拌将外卖、拌将水煮菜、干拌、麻辣烫、冒菜、麻辣香锅、卤味 |
| 汤粥清淡 | 粥、汤饭、蒸菜、汤粉、轻食、沙拉、炖汤 |
| 其他正餐 | 火锅、烧烤、日料、东南亚菜、西餐、茶餐厅、融合菜 |

查询模板：

```text
“<空间锚点> <该组查询词> 门店 地址”
```

- 不混入“推荐、榜单、网红、必吃、评分最高”等词。
- 摘要出现具体店名、分店或地址线索即可进入候选台账，后续再核验。
- 搜索平台、出现顺序和摘要排名一律只是来源属性，不构成质量权重。
- 外卖型品牌可能没有沿街店招。外卖分支发现品牌线索时，用补查额度执行“`<空间锚点> <品牌> 外卖 地址 送达范围`”。

## 五、正餐网页矩阵与停止条件

- 正餐基础补漏矩阵固定为 `3个空间锚点 × 7组餐型 = 21个逻辑查询`；饮料不得重复执行本矩阵，改用饮料协议的15格或9格矩阵。
- 21格完成前不得推荐、打分或按评分删店；地图候选与网页候选同时保持平铺。
- 完成基础矩阵后最多执行3次补查，优先空白餐型、地址不清、用户已知漏店或疑似错分店。
- 用户给出已知漏店时，至少执行一次“`<空间锚点> <完整店名> 地址`”和一次“`<空间锚点> <完整店名> 到店/外卖`”；两次都计入补查上限。
- 连续3次补查没有新增有效门店时，网页补漏结束。
- 达到24次且最后一次仍有新增门店时，整体标记 `coverage_status: incomplete`；先交付临时结果，再询问是否继续深搜。
- 某组没有结果时保留空白记录，不把其他组的店复制过去充数。

## 六、统一候选台账

每家门店至少记录：

```text
名称｜分店｜地址文本｜城市/区｜餐型组｜服务方式（到店/外卖/未知）
高德 POI ID｜直线距离｜空间锚点｜发现查询｜来源URL｜来源类型（高德/网页/截图）
推广/榜单标记｜营业｜价格｜步行/送达｜排队｜座位/包间｜核验状态
```

- 高德结果先按 POI ID去重；同 ID 在周边、分页或网格中出现时合并来源证据。
- 跨来源再用“标准化名称＋分店/完整地址”关联；同品牌不同分店必须保留，地址不明的同名店宁可暂留两条。
- 网页新增而高德没有的门店照常入池，标记“网页补漏”；不得因缺少高德 ID而删除。
- 高德存在而网页没有的门店也照常保留；网页曝光度不是入池门槛。
- 推广、榜单、评分、评论量和网红标签仅作为来源属性，永远不参与排序加分。
- 只有明确位于其他城市、区、超出用户范围或违反硬约束时才删除，并记录原因。
- 只有存在可核验门面或到店信息的候选才能进入“出去吃”排序；只提供配送的候选仅进入“外卖”排序。服务方式无法核验时写“未知”。

## 七、封池后核验与排序

- 高德枚举、候选分页交付与当前分支的网页矩阵都完成后才封闭候选池；正餐为21格，模糊饮料为15格，目标饮料品类为9格。枚举为 `partial` 或分页未取完时，整体覆盖状态仍为“未搜完”。
- 候选池封闭后才调用 `read-page`，先核验排序前10家；失效候选由后续候选递补。
- 核验具体分店的营业、价格、菜单、排队、座位、环境和来源时间，不用品牌总体信息替代分店。
- 高德 `business` 中的营业时间、评分和参考价格只能作为待核验线索，不视为当前营业、实时排队或实际人均。
- 高德 `distance_m` 是 GCJ-02 坐标间的直线距离，不是步行距离或车程；没有路线证据就写“步行：未知”。
- 先执行硬约束过滤，再按 Eatrii 主流程的场景顺序排序。
- 删除推广、榜单、评分、评论量、高德页码和出现顺序后重新排序，结果必须不变。

## 八、覆盖报告

正常输出至少报告：

```text
高德枚举：<状态>｜半径 <N> 米｜POI 请求 <已用>/<预算>｜半径内 <N> 家
网页补漏：<正餐 21/21｜饮料 15/15｜目标品类 9/9，三选一>｜补查 X/3
统一候选池：本轮检索到 N 家｜覆盖状态：已封池/未搜完
```

- 常规回复只显示最相关的10家；用户要求时再展开完整候选池。
- 不得使用“附近全部”“一共只有”“零遗漏”“已穷尽现实门店”等表述。
- 高德状态完整、网页矩阵完整也只能称“本轮已封池”。
- 已知门店未进入候选池即判定本轮高召回测试失败，补充位置锚点、餐型词或完整店名后重跑。

## 九、基准验收

深圳南山云科技大厦是第一组人工真值基准。用户给出已知店名或地图截图后：

1. 先检查门店是否出现在高德 `pois`。
2. 再检查当前分支的21格、15格或9格网页补漏是否发现。
3. 任一已知门店未进入统一台账都记录为召回失败，不用“同类餐型已经有了”替代。
4. 高德枚举达到预算仍持续饱和时，保留 `partial` 与具体原因；需要时由用户确认是否用 `max_poi_requests: 256` 继续深搜。

高德接口约束以官方文档为准：

- POI 2.0：https://developer.amap.com/api/webservice/guide/api-advanced/newpoisearch
- 地理编码：https://developer.amap.com/api/webservice/guide/api/georegeo
- 错误码：https://developer.amap.com/api/webservice/guide/tools/info
