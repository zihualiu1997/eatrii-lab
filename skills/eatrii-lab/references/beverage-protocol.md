# 饮料与下午茶搜索协议

只在用户要决定当前一杯、下午茶饮料或饮料配送时读取。本协议复用 `map-enumerate-nearby` 的餐饮大类平铺召回，不新增高德子类或 MCP 参数；附近门店协议中的位置解析、三个空间锚点、分页、去重、封池与未知字段规则继续有效，本文件只替换正餐网页矩阵并补充饮料排序。

## 一、识别方式与一次性问询

- “点奶茶、点咖啡、送杯喝的”直接识别为 `delivery`。
- “附近喝杯咖啡、下楼买、找地方坐会儿”识别为 `dine_in`，再从语义判断自取或坐店。
- “下午喝啥、来杯什么”未说明方式时，一次询问位置、送过来还是下楼拿/坐店里、人数；乳制品、过敏原与咖啡因限制作为可选项。
- 已知字段不重复询问；用户说“随便”时按近、快、稳、价格适中执行。
- 饮料不能替代用户正在选择的正餐，除非用户明确把饮料作为本次主要目标或要求搭配。

## 二、高德平铺召回

1. 外卖传 `scene: delivery`；自取或坐店传 `scene: dine_in`。
2. 继续枚举完整餐饮大类 `050000`，并取完所有 `next_cursor` 页面。
3. 用 POI 的 `type`、`typecode`、店名与当前菜单识别饮料候选，但不得仅因高德标签不精确删除疑似饮料店。
4. 高德返回顺序、评分、评论量和连锁知名度不参与排序。
5. 地图候选与网页候选全部入池后再过滤、核验和排序。

## 三、饮料网页补漏矩阵

继续使用精确锚点、别名锚点和邻近锚点。

### 模糊饮料需求：15格

执行 `3个空间锚点 × 5组 = 15个逻辑查询`：

| 组别 | 必含词或同义方向 |
|------|------------------|
| 全饮品 | 饮品、饮料、下午茶、喝东西、饮品店 |
| 咖啡 | 咖啡、美式、拿铁、手冲、咖啡店 |
| 奶茶 | 奶茶、轻乳茶、鲜奶茶、珍珠奶茶 |
| 茶与果饮 | 果茶、柠檬茶、纯茶、茶饮、果汁 |
| 无咖啡因与组合 | 无咖啡因、酸奶、糖水、冰品、烘焙、甜点 |

### 已明确品类：9格

用户明确只要咖啡、奶茶或其他单一品类时，执行 `3个空间锚点 × 3组 = 9个逻辑查询`：

1. 全饮品词。
2. 用户指定品类及常见同义词。
3. “本地独立店＋指定品类”，避免只召回高曝光连锁。

查询模板：

```text
“<空间锚点> <该组查询词> 门店 地址 菜单”
```

- 基础矩阵完成前不得推荐或排序。
- 两种矩阵完成后均允许最多3次空白品类、地址不清或已知漏店补查。
- 只有配送线索而无可到店证据的候选只进入外卖池；服务方式未知时保留并标“未知”。

## 四、饮料候选台账

在通用候选字段之外记录：

```text
饮料大类｜具体饮品｜规格｜温度｜糖度/冰量｜咖啡因｜乳制品/过敏原
服务方式｜菜单价｜包装费｜配送费｜起送价｜预计送达/取餐｜运输稳定性
座位/安静度｜活动线索｜活动当天核验状态｜菜单与核验时间
```

- 只有当前菜单支持时才填写具体饮品、规格、温度、糖冰、咖啡因、乳制品或过敏原。
- 没有证据时写“未知”，不得按品牌常识推断。
- 外卖实付必须包含达到起送价的必要消费、包装费和配送费。
- 奶盖、冰沙、冰淇淋、热饮等运输风险需有当前距离或送达证据；不能凭空给出融化、分层或洒漏结论。

## 五、过滤与排序

共同先过滤当前不可买/不可送、明确过敏或忌口冲突，再按场景排序：

| 场景 | 排序顺序 |
|------|----------|
| 外卖 | 预计送达总时长 → 本单实付 → 运输稳定性 → 口味适配 |
| 下楼自取 | 完整取餐时间 → 距离证据 → 单杯/整单实付 → 口味适配 |
| 坐店下午茶 | 座位与安静度 → 饮品/甜点组合 → 距离证据 → 实付价格 |

- 咖啡需求额外考虑用户主动给出的提神、低因或无咖啡因目标。
- 奶茶需求额外考虑用户主动给出的糖度、冰量、乳制品和过敏原限制。
- 经当天官方来源核验的优惠可以改变实付价格；静态活动线索或未核验优惠只能作为提示或同分项，不得改价。
- 新品只作自然备选或同等候选的尝鲜因素，不压过可用性、硬限制、距离或配送。

## 六、输出

输出一个首选、两个不同饮料大类备选和最多十家对比。首选优先落到“具体门店＋具体饮品”；没有当前菜单证据时，不编造具体饮品，明确写“具体饮品待下单页确认”。

饮料比较表至少包含：

```text
候选｜饮料/分店｜单杯或整单实付｜送达/取餐｜运输或座位适配｜糖冰/咖啡因/乳制品｜优惠核验｜未知项
```

覆盖报告使用“饮料矩阵15/15”或“目标品类矩阵9/9”；不得误写成正餐矩阵21/21。
